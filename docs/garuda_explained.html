Global Air Resource & Unified Decision Architecture

A planner you can talk to. Math that does the planning.

GARUDA helps plan and re-plan air operations when the situation changes fast. You ask in plain language. A language model looks up the facts and calls solvers. A person still approves every change to who flies what.

Hackathon prototype One fictional theatre Unclassified synthetic military data Real weather, maps, and civil traffic

The problem

Planning air operations means juggling aircraft, crews, weapons, airspace, weather, threats, and mission priorities. Those facts usually live in different systems, so plans take too long and scarce aircraft get used poorly.

Too many sources

Readiness, weather, threats, and tasking are not in one live picture.

The picture moves

A jet breaks, fog closes a base, a new threat appears, an urgent request arrives. The old plan is stale in minutes.

Scarce airpower

There are never enough flyable jets, rested crews, weapons, or tankers. A good plan is an allocation problem, not a guess.

The big picture

Three layers. Data holds the facts. The language agent is the interface. Solvers and models do the actual numbers.

ONE
RULE
The language model never invents a plan or a number. It retrieves data, calls a tool, and explains what the tool returned. If it does not have the data, it says so.

One story, end to end

This is the whole system in one event. At six hours into the exercise, three aircraft become not mission capable (NMC).

Data layer

The simulator publishes aircraft.status on Redpanda. Consumers update Postgres (the record), Timescale (the history), Neo4j (the links), and Redis (the live snapshot).

Harness

The UI hears the event over a live stream. Someone says “retask.” The router labels this RETASK, not a simple question.

Harness

The planner calls get_mission_requests for the broken tails, then retask_rolling_horizon. Flights already airborne, or launching inside two hours, stay locked.

Optimization

A smaller copy of the assignment problem is solved in seconds. It prefers keeping the old plan, and only moves what the breakdown forces. It returns a diff: who replaced whom, what was dropped, and why.

Critic

A non-LLM checker confirms the solver status, that constraints still hold, that KPIs exist, and that the data is fresh. Then Monte Carlo runs the new plan many times under random failures and weather.

Human

The screen shows the draft, the change from the old plan, the risks, and a few alternative trade-offs. The commander approves or rejects with a comment. Rejection sends the comment back to the planner.

Commit

Approval writes a new plan version, updates the graph, and publishes garuda.plan.event. The language model then explains the result in sentences, citing the tool outputs.

The theatre

A fictional western air front over Rajasthan, Gujarat, and Punjab. Only the geography and public airfield locations are real. Units, strengths, weapons, and threats are invented.

B2 JaisalmerVIJR · forward fighter

B4 AmbalaVIAM · fighter / strike
B5 AdampurVIAX · fighter
B6 BhujVABJ · transport / close support
B7 AgraVIAG · tanker / transport / AWACS
~150 aircraft~300 crew · fixed random seed

Fleet mix, all fictional counts: Su-30MKI 40, Rafale 24, Tejas 24, Mirage-2000 18, Jaguar 12, C-130J 8, IL-78 tankers 6, AWACS 4, helicopters 14. Weapons are generic classes such as a beyond-visual-range missile or a 500 lb guided bomb, with made-up performance.

Layer 1 — what we store

Each domain has one owner. Other databases are copies, fed by the message bus, so they can drift and be rebuilt.

How the fake data is made

A fixed seed (GARUDA_SEED) makes the same world every time. Two stages: a static world, then a clock that keeps moving.

1
Scenario fileBases, fleet mix, horizon, scripted events.
2
Static worldAircraft, crews, weapons, threats, missions, zones. Checked, then loaded.
3
Live simulatorSimPy advances a fake clock, often at 60× speed.
4
Message busEach change is an event on Redpanda.
5
Stores updateConsumers write Postgres, the graph, history, and Redis.

What the clock simulates

Breakdowns (older jets fail more), maintenance finishing, fuel burn and refuel, sortie turnarounds, crew duty and rest, threats that pop up or move, new missions arriving at random, cancellations, and weather overrides. Surge flying raises the failure rate by about 1.3×.

Scripted injections

A button or POST /v1/scenario/inject-event can force a known surprise: aircraft NMC, new SAM, base closed, priority-1 request, tanker lost, or a weather override. Useful for demos, because the outcome is predictable.

Checks before the data is trusted: every aircraft has a base and squadron, weapon loads respect weight limits, and a snapshot with the same seed always matches. Commands: python -m garuda.generate and python -m garuda.simulate --speed 60.

Where each fact lives

Postgres is the authority. If the graph drifts, it is rebuilt from Postgres. The agent never opens a database itself. It calls repositories.

Postgres + PostGIS

The official record: aircraft, crews, weapons, missions, plans, and map shapes.

TimescaleDB

History: status over time, weather grids, tracks. Same Postgres engine, built for time.

Neo4j

“Who is connected to whom.” Qualified crews, mission packages, threat coverage.

Redis

The live board: current status, weapon counters, active threats, pending missions. Rebuilt from Postgres if wiped.

Redpanda

Kafka-compatible bus. Topics like garuda.aircraft.status. Kept 7 days. Latest-state topics are compacted.

MinIO + pgvector

Files (terrain, raw weather) and document chunks for doctrine search.

An event looks like: id, type, entity, time, version, payload. Consumers are safe to replay. Plans and the audit log are kept. Aircraft history is about 90 days. Live civil tracks expire within a day.

Layer 2 — how the agent thinks

LangGraph is a flowchart with memory. FastAPI is the front door. A checkpoint in Postgres lets an approval wait survive a restart.

RouterIs this a question, a new plan, a retask, a what-if, or “explain that”?
RetrieverFor questions: call read-only data tools until it can answer.
PlannerDecides the next tool, or that it is ready to answer. Keeps a scratchpad.
Tool executorRuns the call only if the arguments match the schema. Times out if it runs too long.
CriticNot a language model. Checks constraints, KPIs, freshness, and solver status. Sends it back if something is wrong.
ApprovalPauses. The API says “awaiting approval.” Nothing is tasking until a person continues the graph.
CommitWrites the plan version and publishes the event. Only with a signed approval token.
RespondPlain-language summary. Numbers cite a tool call, like [T3].
MemoryMessages, intent, scenario clock, cached tool results, the draft plan, and a tool-call budget.

Three ways it finds facts

Structured tools are the default (filter aircraft, weather along a route). The graph answers relationship questions. Document search is for procedures: chunks of about 500 words, matched by meaning and by keywords.

It does not drown in data

Tools return totals plus the top rows, not the whole table. Big results get a handle; the model can ask for the next slice. A short cache (30–60 seconds) avoids repeat lookups. The scenario clock and data age are injected every turn.

Questions it can ask

These tools only read. They cannot change tasking. Each one takes one validated object in and returns one object out.

get_aircraft_availability

Which jets can fly?

Filter by base, type, status, or a future time (then it uses the forecast).

get_crew_status

Who is legal to fly?

Qualification, fatigue, and a time window.

get_weapon_stock

What munitions are left?

Stock and legal loadouts per base.

get_airspace

What airspace is hot?

Zones along a route, height, and time.

get_weather_along_route

Can we fly this path?

Ceiling, visibility, wind, storms, and a flyability score.

get_threats_in_area

What is defending this area?

Threats inside a radius or a polygon, above a confidence level.

get_mission_requests

What still needs doing?

Pending and planned missions by priority and window.

get_civil_traffic

Are airliners nearby?

Recent ADS-B tracks in an area.

query_ontology

How are things linked?

A fixed Cypher template plus parameters. No free-form graph queries.

spatial_query

How far, and does it overlap?

Distance, radius, nearest, intersection, buffer. PostGIS does the geometry.

search_doctrine

What do the procedures say?

Top passages from standing documents, with a score.

Human approval and guardrails

GARUDA supports a decision. It does not make one. No tasking change takes effect without an explicit approval, and every step can be audited.

RiskWhat stops it
The model changes the plan by itselfDraft tools write only a draft. commit_plan needs an approval token. The model cannot call commit.
Invented numbersThe critic rejects figures that are not in a tool result. “I don’t have that data” is an allowed answer.
Stale factsEvery result has data_as_of. Warn after 15 minutes for status, 3 hours for weather.
A solver that cheats its own constraintsA separate checker re-validates the plan before anyone sees it.
Prompt injection in a document or a remarkRetrieved text is treated as data. Tool arguments are still checked against the schema.
Too many tool callsA budget per turn, a timeout per tool, and an allow-list by role: Planner, Commander, Observer.
Classified data leaving the buildingThis prototype only sends synthetic data to a cloud model. A redaction layer is the seam for a later air-gapped model.

What a plan must explain

Value breakdown, the constraints that are binding (for example “no bombs left at Jaisalmer”), missions left undone and why (NO_QUALIFIED_CREW, NO_WEAPON_STOCK, WEATHER, THREAT_RISK), a simple sensitivity (“if tanker T2 is lost, value drops by N”), and the timestamps of the data used.

If the solver finds no solution, it reports the smallest set of rules you would have to relax. If it runs out of time, it returns the best plan so far and labels it feasible, not proven best. The audit table is append-only: who, when, which tool, which model, which seed.

The API, in one glance

FastAPI. Solvers run in a process pool so a long solve does not freeze the server. Roles travel in a token. Chat is rate-limited.

Services in Docker: Postgres (with PostGIS, Timescale, and vectors), Neo4j, Redis, Redpanda, MinIO, the API, the generator, and the real-feed ingestor. Grafana is optional.

Layer 3 — the toolbox

Each algorithm is a tool with the same envelope: ok or not, data, warnings, when the data was true, a short explanation, and any error. Search to jump to one.

Build the plan

assign_missions

Match jets to missions

Pick which aircraft, with which weapon load, fly which mission, to maximise priority-weighted value. Respects range, stock, weather, crew, base capacity, and tanker needs. A yes/no linear program (MILP).

MILP · PuLP / HiGHSdraft
compute_sortie_capacity

How many sorties can a base generate?

Counts launches per hour limited by flyable jets, turnaround, ground crew, fuel, munitions, runway, and weather. The tightest limit is the bottleneck. Feeds the assignment tool. Pure linear program, milliseconds.

LP · PuLP / HiGHSread-only
plan_route

Find a path that survives

A grid of cost: distance, threat rings, bad weather, civil traffic, terrain. A* or Theta* finds a path under a risk cap. If none exists, it returns the least-bad path and says so. Also checks fuel, including tanking.

A* / Theta* / RRT*read-only
schedule_crew

Put a legal person in every seat

Qualified, current, not on leave, no overlapping duties, max duty and minimum rest. Prefers lower fatigue and fair flying hours. Two-seat jets stay paired in a squadron. Unfilled seats say why: no one qualified, not enough rest, or medical.

CP-SAT · OR-Toolsdraft
assign_weapons_to_targets

Spend weapons where they matter

Several weapons on one target have diminishing returns. A greedy pass (then a local swap) maximises expected destroyed value without emptying the wrong bunker. An exact MILP exists for smaller cases.

Greedy + MILPdraft
schedule_tanker_aar

Meet receivers with a tanker

Vehicle routing with time windows: a few IL-78s, fuel to give away, orbits that stay outside threat rings, and receivers who must tank inside a window. Reports who did not get fuel, because those missions may have to drop.

VRP · OR-Toolsdraft
deconflict_airspace

Keep flights out of each other

Nudge departure times (within a limit) or change altitude blocks so two flights are not in the same zone at once, zone capacity holds, and civil tracks are avoided. Shifts the important missions as little as possible.

CP-SATdraft
retask_rolling_horizon

Repair the plan after a surprise

Re-solves assignment on a short horizon. Airborne and imminent flights are frozen. A penalty discourages needless changes. Fast mode only frees the missions the event actually touches. Returns a diff and the change in value.

Warm-started MILPdraft
pareto_tradeoffs

Show a few honest options

Value, risk, munitions, fatigue, and disruption compete. Instead of one hidden compromise, it returns up to five plans labelled roughly “max effect,” “balanced,” “min risk,” “min disruption,” plus the swap rate between them.

Epsilon-constraint / NSGA-IIread-only
rl_retask

A learned reflex (stretch)

A policy trained to react to a sequence of failures faster than a full re-solve. Compared head to head with the math retasker. Not the system of record.

PPO · stretch
forecast_availability

Will this jet still be flyable?

Chance each aircraft is fully mission capable at 24, 48, and 72 hours, plus the expected count per base. Trained on the simulator, so plans do not count on jets that are about to break.

XGBoost
predict_component_rul

When might a part fail?

Remaining useful life for engine, radar, hydraulics, avionics. Survival curves (Weibull and Cox) give a low, typical, and high estimate of hours left.

lifelines
assess_crew_fatigue

How tired, now and later?

A simple sleep-and-circadian model, 0 fresh to 1 unfit, plus an optional correction from a small model. Used as a limit inside crew scheduling.

Biomath + ML
predict_weather_impact

Will weather stop the mission?

Go, degraded, or no-go for a mission, using real forecast fields at the base, along the route, and at the target. Cloud hurts laser and infrared weapons more.

LightGBM
detect_threat_anomalies

Something looks unusual

Flags a SAM that jumped, a new cluster, a spike in detections, or a track that does not fit. Alerts when two detectors agree. A hint for the planner, not an automatic retask.

Isolation Forest · HDBSCAN
predict_mission_success

Odds of effect, and of coming home

A fast stand-in for the slow simulator. SHAP lists the drivers: threat on the route, missing SEAD, fatigue, weather, weapon fit.

XGBoost + SHAP
evaluate_plan_monte_carlo

How brittle is this plan?

Runs the plan hundreds of times. Each run samples breakdowns, weather, delays, threat kills, and weapon hits, including cascades (lost SEAD makes the strike riskier). You see the spread: typical value, bad day (5th percentile), and expected losses.

What to build first

The hackathon order is the demo order: a plan you can see, then a surprise you can repair, then the forecasts that make it honest.

  1. Core. Sortie capacity, mission assignment, threat-aware routes.
  2. The story. Crew scheduling, rolling-horizon retask, Monte Carlo.
  3. Honesty. Availability forecast, weather impact, weapon-to-target assignment.
  4. The rest of the package. Tankers, airspace deconfliction, Pareto options.
  5. Later. Component life, fatigue model, threat anomalies, success model, and the reinforcement-learning stretch.

Conventions every tool shares

Pydantic in, Pydantic out. A time limit. A deterministic seed. A status, KPIs, an explanation, and data_as_of. Solver output is checked again by an independent validator before it is shown.

Glossary

FMC / PMC / NMC
Fully, partially, or not mission capable.
AOG
Aircraft on ground. It is not flying.
Sortie
One flight by one aircraft for a mission.
SEAD
Suppression of enemy air defences. Often must fly before a strike.
AAR
Air-to-air refuelling. A tanker gives fuel to a receiver.
TOT
Time on target. When the aircraft should be over the objective.
MILP
Mixed-integer linear program. Yes/no choices (this jet, this mission) under linear limits.
LP
Linear program. Same idea, but the answers can be fractional. Fine for “how many sorties.”
CP-SAT
Constraint solver. Good at schedules: no overlaps, duty limits, separation.
VRP
Vehicle routing problem. Here, tankers visiting refuelling points on time.
Pareto
A set of plans where improving one goal makes another worse. You choose the trade.
RUL
Remaining useful life of a component, in flight hours.
Monte Carlo
Repeat the plan with random failures and weather. The spread is the answer.
HITL
Human in the loop. The graph pauses until a person approves.
RORO
Receive an object, return an object. One schema in, one schema out.
SoR
System of record. The store that owns a fact. Here, Postgres.
